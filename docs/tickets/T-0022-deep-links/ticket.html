Route links into installed mobile apps

Ticket: T-0022. Delivery role: developer. Relative effort: L.

Lifecycle, priority, dependencies, and ticket path are maintained only in the queue, sourced from tickets.jsonl.

Outcome

Let link owners configure iOS and Android app destinations with a web fallback, using platform-verified app links on the configured public primary domain where platform association permits it.

Current evidence

Verified in apps/api/src/index.ts: PUBLIC_BASE_URL is optional; without it the public origin is inferred from the request. There are currently no platform association endpoints or app destination fields. Official platform guidance requires a domain association file and matching app-side configuration. Apple documents the Universal Links association file and entitlement; Android documents App Links verification through Digital Asset Links. The owner explicitly excluded custom-domain management.

Scope and exclusions

V1 stores optional iOS and Android app URLs plus a web fallback for each link, and serves the required domain association file(s) only for the configured primary domain. The owner supplies app identifiers, Apple association data, and Android signing fingerprints. Do not promise detection of whether an app is installed; rely on platform association behavior and a web fallback. No app SDK, custom-domain setup/verification, redirect via unverified custom host, or mobile app development. Grooming must confirm how the app should receive/resolve the short-link slug.

Research, design, and interfaces

Apple associated domains and Android Digital Asset Links require corresponding configuration in the native app and publicly reachable HTTPS domain files. Android's assetlinks.json must be served without redirects. This product cannot change the native app configuration; provide exact generated instructions and validation. See Apple supporting associated domains, Android website association files, and Android app-link verification.
