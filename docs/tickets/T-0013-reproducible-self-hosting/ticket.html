Provide a reproducible self-hosting setup

Ticket: T-0013. Delivery role: developer. Relative effort: L. S = localized addition, M = cross-layer work, L = infrastructure or complex runtime work. These are planning estimates, not commitments.

Lifecycle, priority, dependencies, and ticket path are maintained only in the canonical queue, sourced from tickets.jsonl.

Outcome

Make the selected Node.js, Hono, React, and SQLite application reproducible for a clean local checkout and a documented Docker Compose self-host. Persist application data outside containers, preserve existing Redirect Hub SQLite records during startup/schema upgrades, and clearly document supported configuration, setup, backup, restore, and production boundaries.

Current evidence

  • The owner selected Node.js with Hono and a React frontend in D-005. The implementation is in apps/api/ and apps/web/.
  • The root package declares Node >=22, uses pnpm workspaces, and provides pnpm dev, pnpm build, and pnpm test. A root pnpm-lock.yaml exists. No Dockerfile, Compose file, or checked-in .env.example was found.
  • The Hono API opens SQLite through Node's built-in node:sqlite DatabaseSync. By default, the path is data/redirect-hub.sqlite; DATABASE_PATH overrides it. The API reads PORT, PUBLIC_BASE_URL, COUNTRY_HEADER_PROVIDER, and NODE_ENV. The local MCP client reads REDIRECT_HUB_API_URL, REDIRECT_HUB_API_TOKEN, and REDIRECT_HUB_MCP_ALLOW_WRITES.
  • Database startup creates tables and indexes idempotently and applies conditional ALTER TABLE changes based on PRAGMA table_info; it also backfills workspace memberships in a transaction. This is inline startup schema evolution, not a versioned migration runner. Existing SQLite content can be sensitive and must not be overwritten or used as test data.
  • The T-0025 review and SQLite fixture tests exercise repeat startup against synthetic older-schema databases and preserve existing links/rules/events/tokens. This is repository evidence, not an instruction to access the developer's database.
  • The README documents local pnpm startup, SQLite path, base URL, proxy routing, and trusted Cloudflare country headers. It directs owners to create an account through sign-up; no seed/demo-account script was found. The README also disclaims public exposure until deployment security and release checks are complete.
  • Source inspection on 9 November 2026 confirms apps/api/src/index.ts:412 defines unauthenticated GET /api/health returning {"status":"ok"}. apps/web/vite.config.ts:6–10 proxies /api and /l to http://127.0.0.1:8787 during development.

Primary runtime evidence, checked 9 November 2026: the Node.js v24.22.2 SQLite documentation labels node:sqlite Stability 1.2 (release candidate), with that status introduced in v24.15.0. Its history says the module was added in v22.5.0 and became available without --experimental-sqlite in v22.13.0 while remaining experimental. The v22.23.4 documentation labels it Stability 1.1 (active development). Therefore >=22 alone is an insufficient unflagged support floor, and an LTS runtime does not make this API stable.

The official Node release page recommends Active or Maintenance LTS for production applications. Its linked release schedule records Node 22 Maintenance LTS from 21 October 2025 to end of life on 30 April 2027, Node 24 Maintenance LTS from 20 October 2026 to 30 April 2028, and Node 26 Active LTS from 28 October 2026. These dates are evidence for choosing a supported pinned runtime during delivery, not verification of the app on those versions. Compose scope should follow the checked-in architecture and official Docker Compose documentation.

Scope and exclusions

  • Pin/document the supported Node runtime compatible with node:sqlite and declare the package manager version used by the clean setup. Use the existing lockfile for deterministic dependency installation.
  • Provide a clean local development procedure and a production-oriented Compose path for the React UI, Hono API, and persistent SQLite database. Route UI/API/short-link requests consistently and define service health/startup behavior.
  • Provide a safe non-secret environment example for variables the code actually reads. Document which values are required, defaults, validation, trusted-proxy assumptions, persistence path, backup/restore, upgrade behavior, and operational limitations.
  • Use account sign-up for a new local installation. Keep test/demo data synthetic and opt-in; do not ship a default password or import existing user records.
  • Preserve existing supported Redirect Hub SQLite databases through additive/repeatable schema upgrades, including public slugs and associated data. Do not access data/redirect-hub.sqlite during implementation or verification.
  • Exclude hosted/cloud deployment, TLS/domain ownership, public release, production security certification, a managed database, automated mail, and importing data from the retained Django application. Link/link-routing functionality itself is handled by its owning tickets.

Research, design, and interfaces

  • Keep the first deployment intentionally single-instance with SQLite unless current code/primary runtime constraints make that unsupported; make the restriction explicit.
  • The current Vite dev proxy maps /api and /l to Hono. Production UI serving is not yet configured; the implementation must choose and document a tested static-serving/reverse-proxy arrangement that preserves those paths and same-origin cookies.
  • Current schema evolution lives in apps/api/src/db.ts and uses conditional alters plus transactional backfill; decide during implementation whether to retain this mechanism or introduce versioned migrations, but do not silently lose existing SQLite data.
  • Use only temporary synthetic databases and synthetic accounts/links in all demonstrations and checks. Do not include the historical Django directory as an active runtime or migration source.

Open decisions

  • Node support floor: the developer selects an exact supported LTS runtime/patch and compatible pnpm version, pins the local/container inputs, and records the SQLite API's release-candidate or experimental status for that chosen version. Resolve through V01 and V03 on the chosen runtime, then align engines.node, README and Docker tags. This ticket retains the current SQLite backend; replacing that backend or claiming production stability would change scope and requires a separate decision.
  • Production UI serving topology: select a supported static server/reverse proxy for the React build and route API/redirect paths to Hono. Resolve by implementing and exercising the Compose path; no custom domain or hosted proxy is in scope.
  • Seed/demo experience: current code has public self-signup but no seed script. Default to no seeded account/data; if reproducible demo data is needed, add a separate explicitly synthetic opt-in command and never a shared default password.
  • Migration mechanism: current schema evolution is inline conditional SQL rather than versioned migrations. Preserve supported SQLite data and make repeat startup safe; developer may choose an explicit schema-version runner if it improves future upgrades without expanding this ticket into data import from Django.
