Generate downloadable QR codes for short links

Ticket: T-0004. Delivery role: Full-stack developer. Relative effort: S. S = localized addition, M = cross-layer work, L = infrastructure or complex runtime work. Estimates are planning aids, not commitments.

Lifecycle, priority, dependencies, and ticket path are maintained only in the queue, sourced from tickets.jsonl.

Outcome

From an authorized link detail page, preview and download a QR code that opens the stable public short URL. The first release provides an accessible in-app preview and PNG/SVG downloads, with no custom styling controls.

Current evidence

  • apps/api/src/index.ts is Hono/Node. It validates an optional PUBLIC_BASE_URL as an HTTP(S) origin without path, credentials, query, or fragment. getPublicBaseUrl() falls back to the request URL origin when the setting is absent.
  • The API serialize() function builds shortUrl as {baseUrl}/l/{slug}; the authenticated GET /api/links/:id returns only a link in the selected workspace (404 otherwise). apps/web/src/main.tsx already consumes shortUrl on link details.
  • apps/web/package.json uses React 19 and has no QR dependency. No QR endpoint or image storage exists. Generating in the browser from authorized link data avoids an image API, database changes, and server-side network requests.
  • Because the API can derive a URL from the incoming request when PUBLIC_BASE_URL is unset, the QR must only be offered for a configured canonical public origin. Proposed small API contract: expose a QR-eligible canonical short URL derived only from configuredPublicBase (null when unset); do not derive QR payload from the request host or from the destination URL.

Library evidence: the node-qrcode browser API documentation describes browser canvas/data-URL output and SVG string output. Recommendation: use qrcode in the web app for client-side rendering/export. This is a package recommendation, not an adopted dependency; verify its current maintenance, license, TypeScript compatibility, and bundle impact during implementation.

Scope and exclusions

Depends on T-0002 (done). Include the authorized link detail screen; QR preview; PNG and SVG downloads; an API-provided canonical QR URL that is null unless PUBLIC_BASE_URL is configured; bounded output; and concise README usage/setup notes. Keep the payload equal to the short URL, never the destination. No extra QR service, persistence, remote image generation, redirect-target fetching, or request-host-derived QR is needed.

Exclude brand marks, colors/design editor, custom dimensions, tracking parameters, QR analytics, bulk export, landing-page QR, social previews, and deep-link behavior. Do not change short-link redirect semantics. Destination edits keep the short URL and therefore keep the existing QR valid; scanning it resolves to the link's current destination/routing behavior. Changing the slug or public origin creates a different QR payload; regenerate/download a new code after either change.

Acceptance checks

IDObservable done-check
AC01An owner or authorized read-only workspace member can open QR preview for a link available in that workspace. A link in another workspace remains unavailable through the existing link-detail API (404), and no separate public QR resource or server file is added.
AC02The API exposes a QR payload URL only when PUBLIC_BASE_URL is configured; it is formed from that validated origin plus the link slug. With the setting absent, the UI explains that the owner must configure the public origin and does not render or download a QR based on request host.
AC03Preview, PNG download, and SVG download all encode the exact canonical short URL; PNG export is a fixed 512×512 pixels with a four-module quiet zone, black modules on white, and no user-controlled size. SVG remains vector/scalable and uses the same quiet-zone and contrast defaults. Inputs over 2,048 characters are rejected with a visible message rather than generating an unbounded symbol.
AC04After changing only the destination, the previously downloaded QR still decodes to the same short URL, and opening that URL reaches the updated redirect destination/routing. Changing slug or configured public origin produces a new QR payload on the next load.
AC05QR preview and download controls have programmatic labels, are keyboard operable with visible focus, and expose the encoded URL as selectable text. On narrow screens the preview and actions fit the content column without horizontal scrolling.

Research, design, and interfaces

Recommended flow: a compact “QR code” panel on link details, with a responsive preview, the canonical URL shown as text, and “Download PNG” / “Download SVG” actions. Generate client-side from the API's explicit QR-eligible URL. The image is derived data; do not store it. The payload is a public short URL, so the QR itself does not expose the destination configuration. Use black-on-white defaults and a quiet zone; do not place logos over the code. If no configured origin exists, show setup guidance and no QR actions.

Package suggestion: qrcode (node-qrcode) browser API, using its canvas or PNG data-URL path and SVG string path. Set output dimensions, margin, error-correction level, and colors explicitly; validate payload length before calling the encoder. Sanitization: treat encoder output as generated image data, not HTML; construct SVG download as a Blob with image/svg+xml and a deterministic safe filename based on the slug. Do not fetch or validate the redirect destination from the browser or server.
