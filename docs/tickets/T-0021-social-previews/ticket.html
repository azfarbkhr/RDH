Customize social previews for links

Ticket: T-0021. Delivery role: developer. Relative effort: M.

Lifecycle, priority, dependencies, and ticket path are maintained only in the queue, sourced from tickets.jsonl.

Outcome

Let a link owner set a human-readable social preview title, description, and image so shared short URLs present the intended campaign context.

Current evidence

Verified in apps/api/src/db.ts: link records have name and destination fields but no preview metadata. apps/api/src/index.ts currently answers GET /l/:slug with a 302 redirect; it classifies known preview crawler user agents as bots for analytics, but does not return link-specific HTML metadata. This ticket is not implemented. The owner selected custom social previews; custom domains remain out of scope.

Scope and exclusions

For an owned link, support optional title, description, and image metadata, with a preview and clear/reset action. Design one safe preview response for recognized crawlers while normal visitors retain the existing redirect behavior. No AI copy, workspace templates, logo editor, or custom-domain management. The image should be an externally reachable HTTPS URL for v1; do not fetch arbitrary user-provided URLs server-side.

Acceptance checks

AC04Use the configured PUBLIC_BASE_URL for canonical/preview URLs; do not trust a forwarded or arbitrary request host when generating metadata.
AC05Document preview crawler limitations and cache behavior; preview edits become visible after a bounded documented cache interval or invalidation action.

Research, design, and interfaces

Social crawlers commonly cache unfurls and may use distinct fetch paths. Verify the selected crawler set and metadata fields during implementation. Design metadata response using safe server-rendered HTML; avoid relying on client-side JavaScript for crawler extraction. Reference the feature research.
