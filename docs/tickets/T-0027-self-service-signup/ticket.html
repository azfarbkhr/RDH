Enable self-service account sign-up

Outcome

Let visitors create their own account from the sign-in screen, so an initialized instance is not limited to its first account. Each account remains a separate owner with its own links, routing rules, tokens, and analytics.

Current evidence

  • Verified in apps/api/src/index.ts: POST /api/auth/register rejects a registration once any user exists (409). It validates email/password, hashes passwords with scrypt, starts a session on success, and assigns every link with a null owner to the registering account.
  • Verified in apps/web/src/main.tsx: when configured, AuthPanel defaults to sign-in. It has no sign-up toggle and displays “This instance is private. Ask its owner for an account.” Registration is only selected automatically when no account exists.
  • Verified in apps/api/src/index.ts: authenticated link, rule, token, tag, and analytics operations use the current session/token's user ID. Link-by-ID lookups include both link ID and owner ID. This supplies existing account isolation that must remain true.
  • Verified in README.md and docs/technical/index.html: both state that only the first account can register; the technical page describes a single-owner instance. Those claims become stale if this ticket ships.

Inference: Self-signup creates a standalone owner account. It does not join an existing account's workspace; workspace membership is a separate invitation feature.

Scope and exclusions

  • Allow a new, unique email/password account to register whether or not other accounts already exist.
  • Add visible, keyboard-operable Sign up and Sign in mode controls to the existing authentication panel; remove the exact private-instance message and describe the account/workspace accurately.
  • Retain first-account bootstrap behavior for any legacy links whose owner_id is null. Later registrations must not claim unowned links or any records already owned by another account. Determine first-account status within the registration transaction to avoid concurrent first registrations both adopting data.
  • New accounts own an isolated workspace. Do not add sharing, roles, invitations, email verification, password recovery, two-factor auth, or account administration; these are separate proposals.
  • Do not claim the instance is safe for public deployment. Registration throttling is outside this ticket; document the current deployment boundary and leave rate limiting as a follow-up.

Delivery owner: Developer. Dependencies: None.

Research, design, and interfaces

Use the existing POST /api/auth/register contract, email normalization, scrypt hash, and session cookie. Within BEGIN IMMEDIATE, check whether any user exists, insert the account, and only associate null-owner legacy links if the database had no users before this registration; do not move that migration outside the transaction. Map duplicate-email uniqueness conflicts to the current non-sensitive 409 response. Preserve the existing user ID on every authenticated query. In the React panel, make the two modes explicit and keep the twelve-character minimum aligned with API validation. Do not invent new authorization roles: each successful signup is an independent owner.
