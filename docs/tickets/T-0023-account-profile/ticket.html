Manage account name, email, and password

Ticket: T-0023. Delivery role: developer. Relative effort: M.

Lifecycle, priority, dependencies, and ticket path are maintained only in the queue, sourced from tickets.jsonl.

Outcome

Allow an authenticated user to update their display name, email address, and password from account settings.

Current evidence

Verified in apps/api/src/db.ts: users stores email and scrypt password salt/hash but no display name. The registration endpoint creates the only account allowed on an instance. Session cookies last 30 days. In apps/api/src/index.ts there are register, login, logout, and session endpoints but no profile-update or password-change route; apps/web/src/main.tsx shows only the email and sign-out control. No email delivery or verification provider is configured in the current app.

Scope and exclusions

Self-service display-name, login-email, and password changes in a dedicated account settings screen. Require reauthentication for credential changes; verify a new email before making it the login address. Include the mechanism to deliver a verification code/link as a documented deployment setting. No account deletion, SSO, administrative user management, invitations, or 2FA implementation (separate tickets).

Acceptance checks

IDObservable done-check
AC01The authenticated user can set and clear an optional display name; persisted value appears in account UI and session response.
AC02Email change begins only after current-password reauthentication; the new address remains pending until verified and the old address remains usable until then.
AC03Password change verifies the current password, enforces the existing minimum 12-character policy and maximum length, and invalidates prior sessions except the current session or explicitly documents the chosen safe session policy.
AC04Account update endpoints cannot access or change another user's record; responses avoid leaking whether unverified email addresses are registered.
AC05Failed verification, duplicate email, invalid current password, and expired confirmation produce clear, non-sensitive feedback; the account remains usable.

Research, design, and interfaces

Use the existing signed-in session and user ID. Email confirmation requires a configurable delivery path, which does not exist in current code. Avoid logging confirmation tokens or password values. Ensure recovery/session revocation behavior is explicit and documented.
