Invite users with expiring links

Ticket: T-0025. Delivery role: developer. Relative effort: M.

Lifecycle, priority, dependencies, and ticket path are maintained only in the queue, sourced from tickets.jsonl.

Outcome

An owner can create and manually share a single-use invitation link. A recipient redeems it by creating an email/password account and joins the owner's workspace with read-only access to its links, routing configuration, tags, and workspace analytics. The invite expires exactly seven days after creation, can be revoked by its owner, and is never sent by the service.

Current evidence

  • apps/api/src/db.ts: accounts are independent; links, tags, and API tokens are user-owned. Rules and click events reference links. There are no workspaces, memberships, or invitations.
  • apps/api/src/index.ts: the T-0027 code change allows multiple email/password accounts. Registration only adopts legacy links with a null owner_id for the first account; later accounts remain isolated. Session authentication sets userId and sessionAuth; bearer API tokens set sessionAuth=false. Read routes scope links, tags, and analytics to userId; mutations also require matching link ownership.
  • apps/api/src/mcp.ts: MCP tools call the authenticated API and include read tools plus optional write tools. A membership must not inherit a user's API-token or MCP access.
  • apps/web/src/main.tsx: the UI supports account registration/sign-in and currently presents Overview, Links, Analytics, and Developer areas. Link detail exposes overview, routing, analytics placeholder, and settings views.
  • apps/api/tests/self-service-signup.test.ts: existing signup checks preserve first-account adoption and verify later accounts do not gain another account's links.
  • D-008 resolves access and redemption: read-only links/analytics UI, account creation during redemption, no email, unverified entered email, no invitee API/MCP, and a seven-day manually shared bearer link.

Implication: “move the existing single owner into a workspace” is stale. Migration must create a private workspace for every existing user and preserve each user's records; it must not merge the independent accounts introduced by T-0027. New independent signup must also provision a private workspace. Invitations then add membership in the inviter's workspace without changing record ownership semantics or breaking owner-only API/MCP identity.

T-0027 baseline and dependency: T-0027's multi-account/auth implementation is present in baseline commit 8f63bb5; T-0025 must preserve that behavior and its legacy first-account adoption rule. T-0025 has no implementation dependency on closing the public self-sign-up UI ticket: invitation redemption creates the new account directly in its own flow. Workspace provisioning must cover both ordinary account registration and invitation redemption so each new account receives its private workspace before any invited membership is added. This is an integration requirement for T-0025, not a queue dependency on T-0027.

Scope and exclusions

  • Owner-only create/list/revoke invitation management; show the raw link only at creation and provide a copy action.
  • Manual invitation URL, exactly seven 24-hour days of validity, single-use redemption into a newly created account, and one read-only membership.
  • Workspace-scoped read access for links, their routing rules and tags, and existing workspace analytics. UI must visibly identify the current workspace and read-only access.
  • Preserve per-user API-token/MCP authorization. Invitees do not receive API/MCP access, token creation, or invitation management.
  • Exclude email delivery/verification, existing-account redemption, multiple roles, member removal/management, SSO, audit logs, custom domains, and per-link analytics implementation. The owner can revoke an unused invitation; membership removal is outside this ticket.

Authorization and redemption contract

  • Resolve an authenticated principal to a workspace membership and role on every protected request. Workspace ID must come from verified membership, never an untrusted request field. Owners may act as today; members can only use explicit workspace-scoped read operations.
  • Apply the member policy at the API boundary as well as in the UI. Include both session and bearer-token paths, API-token management endpoints, routing simulator, and MCP tools in the authorization review. UI hiding alone is insufficient.
  • Use an unpredictable, cryptographically generated bearer secret and store only a one-way hash. Fragment-to-POST handling is mandatory: put the secret in the URL fragment, read it client-side, POST it only in the body, replace the current history entry to clear the fragment before sending, and clear transient UI/component state after the attempt. Never put it in a path/query/request URL or referrer. Redact it from access/application logs, errors, analytics, all redemption responses, and invitation listings; only the initial create response may return the copyable URL.
  • Redeem inside a transaction with a database-enforced single-use update/constraint and conditional expiry/revocation checks. Concurrent redemption must not create two users/memberships. Failed transactions must roll back user, membership, and redemption state together.
  • Workspace migration must be safe to rerun and must preserve current user-owned records and token identity. Schema changes may replace owner_id with workspace references or keep ownership as creator metadata, but all reads/writes must enforce workspace membership. Do not make a user-owned API token implicitly authorize every workspace the user joins.
