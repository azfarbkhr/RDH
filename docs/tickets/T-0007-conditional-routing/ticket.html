Implement a shared country and device routing resolver

Ticket: T-0007. Delivery role: developer. Relative effort: L. S = localized addition, M = cross-layer work, L = infrastructure or complex runtime work. These are planning estimates, not commitments.

Lifecycle, priority, dependencies, and ticket path are maintained only in the queue, sourced from tickets.jsonl.

Outcome

Create one resolver used by actual redirects and simulation. Support ordered country and device/OS rules with AND within a rule, first match wins, and a required default destination. Apply lifecycle, password gate where enabled, route selection, and UTM composition in that order.

Current evidence

The current Django model has an owner, target URL, unique short code, and timestamps. The current redirect view selects a single destination. The inspected test module is a placeholder. Proposed behavior above is not implemented by this ticket document.

Feature inspiration: Dub create-link reference, inspected 8 November 2026. The scope and effort are Redirect Hub recommendations, not claims about Dub implementation cost. See research and source limits and owner direction and planning assumptions.

Scope and exclusions

No city precision, arbitrary expression language, IP access-control claim, or server-side fetching of targets.

Acceptance checks

IDObservable done-check
AC01Evaluate deterministic ordered rules and return destination, matched rule ID, and a trace. Unknown visitor data falls through to another matching rule or default.
AC02Derive real visitor context using a configured country database and explicit trusted-proxy policy. Client-supplied geography headers are ignored unless the proxy is trusted.
AC03Use temporary redirects for mutable destinations, validate supported http/https targets, and reject direct self-redirects. Simulation has no redirect or analytics side effects.
