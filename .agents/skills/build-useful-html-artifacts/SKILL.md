# Build Useful HTML Artifacts

Use this skill whenever research findings or other task results need to be presented. Always produce a durable HTML artifact as the canonical deliverable; do not create a parallel Markdown report for the same findings. The chat response must give a short summary and link to the HTML file.

This skill is only about how the html artifacts should be structure to display information clearly. For writing, please apply `clear-effective-writing` skill available in same folder. 
This skill sets principles to follow and not provide fixed template yet.

## Choosing HTML components

- Use headings and short text to organize explanations; use lists for a few related points or steps.
- Use a table for structured comparisons, a chart for meaningful patterns or changes, and a diagram for relationships or processes. Choose the simplest component that makes the information easier to understand.
- If presenting a grid or table, use an `ID` first column and simple sequential row numbers (`1`, `2`, `3`, ...).
- Use a callout for a takeaway that needs emphasis and expandable details for useful supporting material that should stay out of the reader's way.
- Keep each section or visual focused on one main point. Keep the design clean and omit details or elements that do not help the reader understand, decide, or act.

## Research report flow

- For a research report, give readers a scannable overview of the main chapters, using takeaway-led headings and a short cue for what each covers. Arrange the chapters so each one naturally leads to the next.
- Let readers open or navigate to a chapter for its evidence and detail. Keep the overview concise and reveal detail progressively so readers can follow the story without facing the full report at once.

## Page design

- Keep the page focused on the reader's question. Use clear headings, readable typography, whitespace, and restrained visual emphasis.
- Make the main conclusion and key evidence visible without requiring interaction. Use expandable details, filters, or other controls only when they materially help readers explore a substantial amount of information.
- Make interactive elements keyboard accessible and usable at narrow screen widths. Prefer simple HTML, CSS, and JavaScript; add a dependency only when it materially improves the result.
- Preserve useful design choices when revising an existing artifact unless the user asks for a redesign.
